# Source the catalog from IGDB through a scheduled Catalog Import

The Game Catalog used to be a static seed that identified games by slug and was upserted as part of the deploy. It is replaced by a Catalog Import whose identity is the **IGDB id**: one run fetches every candidate through the Game Catalog Source port, checks that the candidates can sustain today's catalog, and only then upserts, delists and relists games in one transaction.

The safety checks run inside the same transaction as the writes, before the first write, after the run takes a transaction-scoped PostgreSQL advisory lock: candidates must reach a configured fraction of today's Listed Games and an absolute floor that also covers the first run. A second concurrent run waits for the first to commit, so both cannot pass on the same stale count. An explicit override bypasses only the fraction check, never the floor. Rows without an IGDB id are legacy rows: they stay delisted and untouched so Squads that reference them keep rendering, while the import only addresses rows by IGDB id.

The curated squad-size and featured list is injected by the factory and wins over source data, with its maximum clamped to 40 players; otherwise the largest online co-op/online capacity between 2 and 40 becomes the squad size, and anything else falls back to 2–5. Admission to the catalog still depends on IGDB's `total_rating_count`, but the stored `popularity` measures what people play now: the source returns the raw IGDB Playing and Steam 24hr Peak Players signals of each candidate, and the Catalog Import turns them into a percentile per signal among the candidates that have it, keeping the higher of the two as an integer from 0 to 10000 (0 for a game with neither signal).

The IGDB implementation arrives in CCC-90 and the schedule in CCC-91; the port keeps the import provable against a fake source today and lets the source be swapped without touching the catalog rules.

The import also brings each game's **platforms** (issue #98). The source asks IGDB for the platform ids of every candidate and maps them to the fixed `Platform` list of `@squadzr/schemas` (Windows, Mac and Linux are PC; Android and iOS are Mobile), without repeats and in display order; ids outside the list, such as PS3, Xbox 360 and Wii U, are ignored. The candidate carries the resulting `platforms` and the upsert writes them to `games.platforms`, so a returning game gets them refreshed. Admission to the catalog does not look at platforms: a game with none of the supported ones stays listed with an empty list, and its Squads then carry no platform. The local import and the scheduled one share this path, so nothing changes in the schedule.

The import also brings each game's **alternative names** (issue #100). The source asks IGDB for `alternative_names.name` and the candidate carries them as `aliases` (an empty list when the field is absent), because acronyms and regional titles such as "CS2" are what players type. A small manual map in the interface layer, keyed by IGDB id and injected into the Catalog Import by the factory like the curated list, adds the acronyms IGDB does not list ("lol", "r6", "wow"). The use case merges both lists and the repository stores them normalized, without repeats and without the game's own name, next to a `search_text` column that Game Search matches. Admission to the catalog and the schedule do not change, and a game's aliases are rewritten on every run.
