# Host the client on Cloudflare Workers and the API on Railway

The Next.js client runs on a Cloudflare Worker at `squadzr.app`. The single Fastify instance and PostgreSQL run on Railway, in one `production` environment, and the API is reached at `api.squadzr.app` through Cloudflare's proxy and a Cloudflare Tunnel: the API has no public address on Railway. Vercel is no longer used, and there is no staging environment. This supersedes [ADR 0002](0002-keep-vercel-and-railway-hosting.md).

We decided eight things:

1. **The client is a Worker named `squadzr-web`, built with vinext.** [vinext](https://github.com/cloudflare/vinext) is Cloudflare's documented default for running a Next.js app on Workers. It runs next to the Next config (`client/vite.config.ts`, `client/cloudflare.config.ts`); `next dev`, `next build` and the CI `build` gate are unchanged. A spike (#132) rendered every page correctly on it. No page fits Workers Free (10 ms CPU per request; the measured medians were 14 to 27 ms), so the Worker runs on Workers Paid (US$ 5 a month).
2. **The Worker has no KV namespace and no Images binding.** Without a data cache adapter, a `revalidate` fetch keeps its response in the memory of each isolate for its five minutes. The only such call is the landing's popular games, one small public read, so a cold isolate costs one API call. Without an image optimizer, `next/image` renders the Discord avatar as a plain `<img>` of the original CDN URL, and no request reaches `/_next/image`. Nothing in the app needs either binding, and both would add a resource to keep.
3. **GitHub Actions deploys the Worker, after CI.** `.github/workflows/deploy-client.yml` runs when the CI workflow succeeds on a push to `main`, and deploys the commit CI tested. Workers Builds is not used: it deploys on push without waiting for checks. `main` is promotion-only, so a deploy is a merged promotion pull request, and a push to `development` deploys nothing. The API follows the same rule through Railway's "Wait for CI".
4. **The API refuses a request that did not come through Cloudflare.** A Transform Rule on `api.squadzr.app` overwrites the `x-squadzr-edge-auth` header with a secret on everything it forwards, and the API, when `EDGE_AUTH_TOKEN` is set, answers 403 to a request without the matching value (the two health routes aside, which Railway probes directly). The Next server sends the same secret on its own calls, from a Worker secret, so the lock does not depend on how Cloudflare routes Worker subrequests. The Transform Rule, the Worker secret and `EDGE_AUTH_TOKEN` are one value and change together.
5. **The visitor's address is `CF-Connecting-IP`, believed only behind the lock.** The API believes only the `x-forwarded-for` entries its own proxy appended, counted by `TRUST_PROXY_HOPS`, which stays at 1 (`cloudflared`, the only proxy in front of the API). `cloudflared` forwards the chain Cloudflare's edge wrote, so at one hop it names the visitor too (measured on the hosted API), but the chain is only the fallback: a Worker's subrequest names the Worker there. `CF-Connecting-IP` is the visitor's address for browsers and Workers alike, and anyone who reaches the origin some other way can write it, so the API adopts it only on a request whose edge secret matched. The app and the API share the parent domain `squadzr.app` (`BETTER_AUTH_COOKIE_DOMAIN`), so the session cookie reaches the Next server and is `SameSite=Lax`. Both amendments of ADR 0002 (the cookie domain and the proxy hops) live here now, with the proxy-hops rule rewritten for Cloudflare.
6. **The API limits abuse itself, per visitor.** The Free Cloudflare plan allows one rate limiting rule, so it keeps guarding sign-in and the API counts the rest: every route allows 300 requests a minute per client address, a WebSocket upgrade 20 a minute, and an address may hold 10 sockets at once (`RATE_LIMIT_MAX`, `WS_UPGRADES_PER_MINUTE`, `WS_MAX_CONNECTIONS_PER_IP`). Server renders are not exempted, because a page view becomes several API calls and hammering pages is the amplification worth limiting. A server call that is not revalidated (a viewer's, or an anonymous read such as the invite preview) carries the visitor's address in `x-real-ip`, which Cloudflare turns into the `CF-Connecting-IP` of a Worker subrequest to the same zone, so a visitor spends their own quota. No header a client can write is trusted: the `CF-Worker` header is not used, and a WAF rule blocks requests that another zone's Worker made (`cf.worker.upstream_zone`).
7. **One `production` environment.** Until launch it has no real users and is the test target. A temporary Railway environment can be created for a risky change.
8. **The API has no public address: Cloudflare reaches it through a Cloudflare Tunnel.** A `cloudflared` service in `.railway/railway.ts` (the official image, pinned to an exact version, two replicas of 0.25 vCPU and 128 MiB at most) holds a remotely managed tunnel, `squadzr-api`, and routes `api.squadzr.app` to `http://api.railway.internal:3000` over Railway's private network. The `api` service has no Railway domain, public or custom, so traffic that skips Cloudflare has nowhere to land; the API listens on `::` (`HOST`) because the private network can be IPv6-only, which is also dual-stack IPv4 for Railway's health check. `api.squadzr.app` is a proxied CNAME to `<tunnel id>.cfargotunnel.com`, so the Transform Rule, the sign-in rate limiting rule and the foreign-Worker WAF rule still match it, and the secret header of point 4 stays as a second layer. The tunnel token is a `preserve()`d variable (`TUNNEL_TOKEN`) set in Railway; tunnels are free on every Cloudflare plan, and the two replicas cost well under US$ 1 a month of Railway usage. The tunnel and its ingress rule live in Cloudflare, outside the repository, like the zone's rules.

## Consequences

The client now depends on a Workers adapter and, on the Cloudflare path, vinext replaces the Next runtime in production. [ADR 0004](0004-run-the-client-on-next-app-router.md) says the client uses no hosting-specific APIs; that still holds for the source (no `cloudflare:workers` import, no Cloudflare package imported by application code), but the production runtime is no longer Next's own, and the build adds `vinext`, `@vinext/cloudflare`, `vite` and the Cloudflare Vite plugin, several of them beta. A move to another host stays a hosting change, but a Next feature vinext does not implement stops working on the Worker before it stops working on Next. The spike lists the known differences from stock Next (no `x-powered-by`, a larger `<head>`, no image resizing).

Cloudflare owns the zone's rules outside this repository: the Transform Rule, the rate limiting rule the Free plan allows (sign-in and OAuth callback), the WAF rule on other zones' Workers, the `www.squadzr.app` redirect, the DNS records and the tunnel with its ingress rule. [The runbook](../ops/client-on-cloudflare-workers.md) lists them and the rotation of the edge secret; [the API runbook](../ops/catalog-import-railway.md) covers the tunnel, rotating its token and rolling back to a public domain.

The API now depends on `cloudflared` being up. Two replicas keep one failing agent from taking it down (a stopped replica was tested with the site up), but the tunnel is a second service to keep running, and the rollback to a public Railway domain waits for Railway to issue a certificate.

The hosting cost is Railway's usage plus Workers Paid.
